# Root cause — FOSSSMBBUN-88 / multi-tab mpass_bridge race

## Scope

Scoped to **L3 (oauth2-proxy session/cookie scope) + L4 (mpass-auth-proxy
bridge state)**, per the bootstrap. Skipped L1 browser code, L2 Traefik
routing, L5 app backends (Plane / Outline / Penpot / SurfSense / Twenty),
and L6 storage — none of them touch `mpass_bridge`. The symptom string
`Missing mpass_bridge cookie` is emitted by exactly one place in the
codebase (the mpass-auth-proxy `/mpass-callback` handler), so the
investigation could be narrowed to that file plus the openspec
session-lifecycle module.

## Symptom

User opens two tabs against the SSO entry (`MAIN_URL`, or any app such
as `pm.${PLATFORM_DOMAIN}`). Both tabs sit on the mPass / Cognito IDP
method picker. The user logs in as user A in tab 1 (succeeds, lands on
the app). The user then submits login as user B in tab 2. Tab 2 shows
the literal page body:

> `Missing mpass_bridge cookie`

This is an HTTP 400 from `mpass-auth-proxy` (`auth.${PLATFORM_DOMAIN}/mpass-callback`),
returned as `text/plain` content. The reporter's expected behaviour is
that tab 2 should be redirected to the app honouring user A's existing
`_oauth2_proxy` session (because cookies are shared across tabs in the
same browser context).

## Request trace

  L1 (browser): innocent. Cookie jar is shared by both tabs in the same
  context, which is normal browser semantics — the bug exists *because*
  of this sharing, not despite it. Nothing in the browser is wrong; it
  faithfully presents whatever `mpass_bridge` value the server last
  Set-Cookie'd.

  L2 (Traefik): innocent. The priority-200 `mpass-bridge` router
  (foss-server-bundle/docker-compose.yml:372) correctly routes
  `/authorize` and `/mpass-callback` on `auth.${PLATFORM_DOMAIN}` to
  `mpass-auth-proxy:8000`. No routing or middleware-chain issue.

  L3 (oauth2-proxy): innocent for the symptom, but it is the *trigger*
  layer. Each tab's first request fires its own OAuth-flow start at
  oauth2-proxy, which produces an independent `state` query parameter
  (`OAUTH2_PROXY_ENCODE_STATE: "true"` at
  foss-server-bundle/docker-compose.yml:433) and redirects the browser
  to `OAUTH2_PROXY_LOGIN_URL` =
  `https://auth.${PLATFORM_DOMAIN}/authorize?state=...`
  (foss-server-bundle/docker-compose.yml:435). The shared
  `_oauth2_proxy` session cookie is scoped to `.${PLATFORM_DOMAIN}`
  (foss-server-bundle/docker-compose.yml:415-416), so after tab 1
  succeeds tab 2 *does* hold a valid Layer-1 cookie — but tab 2's
  flow never reaches oauth2-proxy's `/oauth2/callback` to notice
  that, because it dies one hop earlier at the bridge callback.

  L4 (mpass-auth-proxy / mPass / Cognito): **implicated**. Single
  shared `mpass_bridge` cookie with no per-tab namespacing. See "Root
  cause" below.

  L5 (app backend): not reached. The bridge fails before tab 2's flow
  ever leaves `auth.${PLATFORM_DOMAIN}`.

  L6 (storage / data): innocent. Redis (Valkey) bridge-state entries
  are keyed by per-flow `state` (`bridge_state:{state}` —
  foss-server-bundle/mpass-auth-proxy/main.py:182), so both tabs' entries
  coexist in Redis. The breakage is purely in *which* state the browser
  cookie points at, not in storage.

## Root cause

The `mpass_bridge` cookie is a **single shared per-context state slot**:
`mpass-auth-proxy`'s `/authorize` handler unconditionally writes
`mpass_bridge=<state>` to a cookie scoped to `.${PLATFORM_DOMAIN}` with
no per-tab discriminator, so the second tab's call to `/authorize`
overwrites the first tab's value (and vice-versa), and any tab that
later reaches `/mpass-callback` runs `redis_client.getdel(...)` and
`response.delete_cookie("mpass_bridge", ...)` (atomically consuming the
*other* tab's bridge entry and then wiping the cookie altogether), so
the surviving tab arrives at `/mpass-callback` with no cookie and is
rejected at `foss-server-bundle/mpass-auth-proxy/main.py:207-209`.

Specific lines:

- Set: `foss-server-bundle/mpass-auth-proxy/main.py:185-194`
  (`response.set_cookie("mpass_bridge", state, domain=COOKIE_DOMAIN, ...)`).
- Read + reject: `foss-server-bundle/mpass-auth-proxy/main.py:207-209`
  (`if not bridge_key: return Response(status_code=400, content="Missing mpass_bridge cookie")`).
- Atomic consume of state: `foss-server-bundle/mpass-auth-proxy/main.py:211`
  (`raw_state = await redis_client.getdel(f"bridge_state:{bridge_key}")`).
- Cookie cleared on success: `foss-server-bundle/mpass-auth-proxy/main.py:266`
  (`response.delete_cookie("mpass_bridge", domain=COOKIE_DOMAIN, path="/")`).

Concrete two-tab failure sequence (the simplest interleaving that
matches the reporter's repro):

1. Tab 1 hits `/authorize?state=S1` → server stores `bridge_state:S1` in
   Redis and Set-Cookie's `mpass_bridge=S1`.
2. Tab 2 hits `/authorize?state=S2` → server stores `bridge_state:S2`
   and Set-Cookie's `mpass_bridge=S2` (overwriting S1 in the shared
   cookie jar — both tabs now present `S2`).
3. User completes login in tab 1. Browser sends `mpass_bridge=S2` (!)
   to `/mpass-callback`. Server does `getdel("bridge_state:S2")` —
   deleting **tab 2's** bridge entry — then clears the cookie.
   The redirect goes back to oauth2-proxy with `state=S1` (from the
   IdP response), which **doesn't match** the consumed S2 state. Two
   possible outcomes here depending on oauth2-proxy's state check:
   tab 1 either errors at oauth2-proxy's state-mismatch path, or
   succeeds because oauth2-proxy treats the upstream-state echo as
   authoritative. Either way, tab 2 is already broken.
4. User submits login in tab 2. Cookie is absent. `/mpass-callback`
   returns 400 `"Missing mpass_bridge cookie"`. Even if the cookie had
   survived, the bridge entry behind it was the one tab 1 just
   `getdel`'d, so the next failure mode would be the 400
   `"Bridge state expired or not found"` at line 213.

The cookie's `SameSite=Lax`, `Secure`, `HttpOnly`, and 600-second
`max-age` are not implicated — those just govern how the browser
attaches the cookie. The bug is structural: there is exactly one
`mpass_bridge` slot per origin, and the design assumes one
in-flight OAuth flow per browser context.

The openspec `session-lifecycle/spec.md` covers the bridge-state TTL
(spec.md:153 "Requirement: bridge state TTL SHALL be 3 minutes") but
**does not define concurrent / multi-tab semantics for the bridge
cookie**. No requirement says "the bridge MUST tolerate two
simultaneous in-flight flows in the same browser context", nor "the
second tab MUST honour the existing `_oauth2_proxy` session and skip
the bridge entirely". This is an unspecified contract.

## Fix location

This is fixable in our own code (mpass-auth-proxy) and is **not** an
upstream Cognito / mPass bug — Cognito's hosted UI doesn't write
`mpass_bridge`; we do.

Two complementary changes are needed; the second is mandatory, the
first is a defence-in-depth:

1. **Repo:** `foss-server-bundle` (and mirror in `foss-server-bundle-devstack`)
   **File:** `mpass-auth-proxy/main.py`
   **Change:** make the bridge cookie per-flow instead of a single
   shared slot. Options that all work:
   - Name the cookie `mpass_bridge_<state>` (or similar) at
     `set_cookie` time (line 185-194) and have `/mpass-callback`
     locate the matching cookie by iterating `request.cookies` for
     the prefix, OR
   - Stop relying on a cookie for the state key entirely: pass the
     state through the IdP redirect (mPass already echoes it as
     part of the OAuth `state` round-trip — that's what oauth2-proxy
     uses) and look it up at `/mpass-callback` from the query string
     instead of from a cookie.
   The second option is cleaner because it removes the cookie-jar
   sharing problem at the root. The cookie was only there to bind
   the IdP callback to the browser flow, but the OAuth `state` round
   trip already provides that binding.

2. **Repo:** `sso-rules-moneta`
   **File:** `openspec/specs/session-lifecycle/spec.md`
   **Change:** add a new requirement defining multi-tab / concurrent
   in-flight bridge-flow semantics. Suggested wording: "the bridge
   cookie or its replacement MUST tolerate N simultaneous in-flight
   OAuth flows in the same browser context; a successful completion
   of one flow MUST NOT invalidate the bridge state of any other
   in-flight flow"; and "WHEN a tab begins a new login while an
   `_oauth2_proxy` cookie is already valid, oauth2-proxy SHOULD
   short-circuit at `/oauth2/start` and redirect back to the app
   without invoking the bridge". Without this, the implementation
   fix in #1 has no contract to match against and the bug class
   can regress.

Do not modify oauth2-proxy itself — its behaviour is fine; the bridge
contract is what's underdefined.

## Class

**code bug** (primary) + **contract gap** (secondary).

The fix lives in code we own (`mpass-auth-proxy/main.py`), but the
underlying root cause is that the openspec session-lifecycle module
never specified the concurrent-tab invariant. The bug-fixer should
land the code fix and the openspec proposal together.

This is **not** an upstream bug — the offending lines are in our
mpass-auth-proxy repo. Cognito and mPass are innocent: they're just
running the OAuth flows we initiate.
